# Incident 2026-08-14 — catalogue reads timing out

Severity :fire: **S1** · 47 min customer impact · authored by @rsilva, reviewed
by @dpham and ~backend

[[_TOC_]]

## Summary

A migration on `imports` took an `ACCESS EXCLUSIVE` lock for the length of a
full table rewrite. Catalogue reads queued behind it and began timing out at the
gateway after 30 s. Nothing was lost; every queued write was applied once the
lock cleared.

## Timeline

>>>
**14:02** — Deploy of !1176 starts. The migration begins rewriting `imports`.

**14:06** — First gateway 504s. Read latency p99 crosses 30 s.

**14:11** — Paged. Initial theory was connection-pool exhaustion, which cost us
about fifteen minutes: pool saturation was a symptom, not the cause.

**14:38** — `pg_locks` shows the migration holding `ACCESS EXCLUSIVE`. The
migration is left to finish rather than cancelled — a rollback mid-rewrite would
have held the same lock for as long again.

**14:49** — Migration commits. Latency recovers within a minute.
>>>

## Root cause

The migration added a column {+`imports.priority`+} with a non-null default. On
this Postgres version that rewrites the table, and `imports` is 41 GB.[^pg]

The change had been reviewed as {-a metadata-only change-} because the staging
copy of `imports` is 300 MB, where the rewrite finished in under a second.

::: details What we expected the plan to be, versus what ran

Reviewed as:

```sql
ALTER TABLE imports ADD COLUMN priority integer;
```

Shipped as:

```sql
ALTER TABLE imports ADD COLUMN priority integer NOT NULL DEFAULT 0;
```

The second form is what forces the rewrite. Adding the column nullable, then
backfilling in batches, then setting the constraint, holds the strong lock only
for the final step.

:::

## What we are changing

- [x] Backfill split into batches, shipped in !1188
- [x] Migration linter rejects `NOT NULL DEFAULT` on any table over 1 GB (!1192)
- [ ] Staging gets a sampled copy of production volumes (#941, ~infrastructure)
- [ ] Gateway sheds read load instead of queueing it (#943, ~"needs review")
- [~] Automatic migration cancellation — rejected, see the discussion on &12

## Follow-ups tracked elsewhere

The gateway work belongs to the platform team and is tracked in

[^pg]: A rewrite is avoided from Postgres 11 onwards for a *constant* default,
    but the default here was applied by a trigger-backed helper, which the
    planner cannot treat as constant.
